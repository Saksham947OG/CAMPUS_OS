**Administration (`COS-ADMIN-001`).** Built (AD-0…AD-5) as a local, single-browser prototype on the owner's instruction "build" (2026-11-01). It is a fourth global store (`campusos:admin:v1`) on the shared plumbing (`service-core`, `service-runner`), with typed variants on one request substrate: **leave** (its own statuses and revisions, one simulated approver stage, and gate departure and return as separate, optional steps) and **tickets** (one engine for facility complaints AND teaching-aid reports, so a teaching report is the same lifecycle plus equipment fields). Leave and ticket statuses are never mapped onto each other. Key rules: a student can never perform a privileged step (every simulator action names the role it plays); a decision is bound to a revision and a status version, so a stale view or an old revision is refused; an edit after approval is a new revision that voids the approval; a reopened ticket stays the same ticket with its history; attachments are name, type and size only; no SLA, team, person or priority is ever invented; and every approval reads "in demo — NOT A VALID GATE PASS". Integrations: My Requests with filters, a deep link `/administration/requests/:id` that forwards to the canonical record, Home My Activity, in-app notifications (once per transition and recipient), and a scoped reset. **Not built:** per-ticket comments, a watermarked sample PDF, an optional personal Calendar block for an absence, course-hub links, and anything server-side. Decisions: DEC-100–DEC-112.

**Shared Experience & Analytics (`COS-SHARED-001`).** Built on the owner's instruction "check and build" (2026-11-02) as a fifth global store (`campusos:shared:v1`) plus per-profile notification preferences, on the shared plumbing. The existing in-app inbox was **extended, not duplicated**: messages gain a category (read off the link), a priority and an optional per-category mute that hides only standard and optional messages, so critical and important ones always show. Exam seating is private to its owner, versioned (every earlier version is kept), flags a contradiction instead of choosing one, and its notice never prints the seat. Best Time to Go uses clearly sample data, shows no recommendation when samples are below a minimum, and never says "live". Time Tax is a scenario calculator with signed (better or worse) differences, totals only per measure and an empty "observations" page, so no measured saving is ever shown.

**Academics (`COS-ACADEMICS-001`).** Built the same day as a sixth global store (`campusos:academics:v1`). Course Hub reads courses, classes and deadlines from the canonical Calendar records and adds sample notices, materials (only a real https link opens; otherwise "Resource not provided"), per-profile read state and private notes. Faculty, BMS Office and club conversations share **one meeting engine** keyed by `actorKind`: a request is never an appointment, a student cannot answer their own request, the simulator is a separate labelled role, stale presses fail, and an accepted meeting is exactly one Calendar entry and one Home activity. Mentorship has private project groups with personal milestones (never official deadlines) and simulated-mentor invitations that are never delivered. F23 (BMS Office) lives under Academics, as this spec places it.

**Community (`COS-COMMUNITY-001`).** Built the same day as a seventh global store (`campusos:community:v1`). Lost & Found keeps private proof fields with the owner, uses category icons instead of pictures, suggests only conservative "Possible match" candidates, separates claim, approval and handover, and ends competing claims without naming a winner. Clubs are fictional, show no contact details, treat following as a preference and use the Academics meeting engine for conversation requests. Sports has teams with captain authority and capacity re-checked at decision time, a distinct simulated committee approval, expiring looking-for-players posts, and fixtures that reschedule under one id with a revision history.

## How to add future modules

1. Workshop/approve scope → create `docs/features/<Feature_Name>_Spec_v1.0.md`.
2. Define feature ID, routes, actor authority, data contract, states, edge cases, integration points, acceptance IDs, non-goals.
3. Mark `DESIGN BASELINE`, then implement a small approved phase.
4. Mark `IMPLEMENTED` only when actually present; `VERIFIED` only with logged test evidence.
5. Keep deferred live demo backend **last**, regardless of how many front-end modules are added.
